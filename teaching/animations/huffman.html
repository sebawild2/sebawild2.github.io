Huffman Codes

Building the Huffman tree from character weights, then encoding and decoding a text with it. The forest is drawn in priority-queue order, so the two tries to merge are always the leftmost two; ties follow the fixed rule in the code panel, so every input has exactly one Huffman tree. Encoding is a table lookup per character; only decoding walks the trie. The tick box in the step bar adds the optional strand on canonical codes and on storing the code itself as bits; the decode view uses those throughout.

Input format

Source text. Anything you type is the source text S; the alphabet ΣS is the set of characters that actually occur in it, and the weights are the character frequencies |S|c. A space is drawn as ␣, a newline as ↵, a tab as ⇥; they are ordinary characters of the alphabet.

Alphabet + weights. One character and one non-negative integer per line, separated by whitespace:

E 1
L 2
O 1
S 4

Use \s for a space character and \\ for a backslash. This mode feeds the weights w straight into Huffman's algorithm, exactly as on the slide where only Σ and w are given. There is no text, so the encoding and decoding phases are skipped and the compression ratio is not defined.

Canonical code and header. The canonical code keeps every codeword length of the Huffman code but reassigns the codewords so that the lengths alone determine them. That is what lets the header store the code as a list of (character, length) pairs rather than a tree. The exact header layout on this page — 8 bits for σ−1, 5 bits for the length-field width b, then σ pairs — is one concrete convention; the slide leaves the details open. The tick box in the step bar switches encoding and decoding between the tree's codewords and the canonical ones; |C| is identical either way, since the lengths are.

Two drawings of the same trie. The step bar switches between the tree and a nested-box picture: a leaf is a box holding its character, and an inner node is a box holding its 0-subtree immediately followed by its 1-subtree. A codeword is then read from the outside in, and the small digits in the corners spell it out; they can be turned off. Box heights follow the height of the subtree, so siblings always line up. The picture is much flatter than the tree — for LOSSLESS 200×126 against 212×222, and for a worst-case path-shaped tree 332×162 against 344×378 — which is what makes it the quicker thing to draw when working an example by hand. In this drawing the priority-queue entries show the tries themselves instead of a name.

Decoding. The decode view takes the complete coded text C — code header followed by body — as a string of 0s and 1s, and is always canonical: the header stores codeword lengths, so only the canonical rule makes the codewords recoverable. Selecting any preset while in this view encodes that example and puts its bits in the box, so the two views are two ways of looking at the same example. A weights preset has no text, so it is realised as one character repeated per unit of weight, which has exactly those frequencies.

Degenerate case. With a one-character alphabet the algorithm performs no merge and the code trie is a single leaf, whose codeword would be the empty string. This page assigns 0 instead, so that the text is still decodable.
