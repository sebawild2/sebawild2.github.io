  The cost model  ·  what counts as a comparison
  

    

      
Sorting is charged its real comparison count, via a counting merge sort — a black box here exactly as
        partition and sort were black boxes on the median-of-medians and Karatsuba pages, not
        animated stroke by stroke. Distance evaluations (d\u2082, in the base cases and the strip check) are counted
        separately and are the same for both variants on the same input: they depend only on which points end up
        compared, not on how the arrays got sorted. The one thing that differs between the two toggles is the sorting
        cost — which is exactly the point.

      
Sort once pays for two sorts (by x, by y) a single time, in the driver, then only ever
        splits already-sorted arrays — no further comparisons. Sort every level re-sorts the current
        subset by x and by y at the start of every recursive call, giving the recurrence
        T(n) = 2T(n/2) + Θ(n log n) instead of T(n) = 2T(n/2) + Θ(n) — an extra log factor that the
        recursion-tree method turns into O(n log² n) overall, exactly the gap the "Divide and Conquer is not all"
        slide flags.

Three fixes to the slide's pseudocode

      
1. The tie-break. Splitting byY by re-testing P[byY[i]].x ≤ m.x can put
        more points on the left than byXₗ actually holds whenever two points share x = m.x —
        the two arrays would then describe different point sets. Fixed by marking, from byX itself, which
        point identities are in the left half, and splitting byY by that mark.

      
2. for i := 0,…,C.size() reads one past the end of C — every
        other loop in this code writes 0,…,n−1; fixed to C.size()−1.

      
3. for j := i+1,…,i+7 has no bound against C.size(); fixed to
        j := i+1,…,min(i+7, C.size()−1).
